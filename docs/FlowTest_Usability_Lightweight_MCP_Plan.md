## 3. 脱敏：默认完全关闭的明确契约

### 3.1 OFF 的含义

默认情况下，下列内容都不得因为“看起来敏感”被系统自动改写、隐藏或拒绝：普通业务参数、组织编号、邮箱、手机号样式字符串、Token、Authorization、Cookie、密码字段、数据库样本、请求/响应样本、说明文本以及合法凭据引用。

此规则适用于系统原本已经有权处理和展示的内容。不新增未授权的数据读取，也不因为 OFF 自动把 Secret 存储中的值解析出来、把完整数据库结果搬给 LLM，或将所有请求体追加到日志。

**OFF 是关闭自动内容处理，不是“扫描之后只告警”。默认路径不运行敏感识别器。**

### 3.2 与其他能力的边界

| 能力 | OFF 时行为 |
|---|---|
| 自动敏感分类、正则扫描、自动遮盖和敏感内容阻断 | 全部不执行 |
| 原有输入、返回和导出中的明文测试值 | 保持原值，不保留 Token 等字段的隐藏例外 |
| 调用者已提供的 `secret://` 引用 | 保持引用形式；OFF 不负责自动解引用 |
| 原本只写不可读的 Secret 存储接口 | 不因此改成可读；这属于资源访问契约，不是脱敏 |
| 数据落盘加密、登录校验、项目权限 | 保留，和展示值是否被改写分离 |
| 请求参数类型、节点引用、表达式执行限制、URL 校验 | 保留，和敏感内容识别分离 |
| 是否记录 Body、保存样本、发送数据给 LLM | 按已有独立采集与输出设置，不因 OFF 自动扩大范围 |
| HTML 转义、HTTP 头编码、Excel 公式防护 | 保留。这些是格式/执行安全要求，不是敏感内容脱敏 |

关闭脱敏后，系统已有的报告、导出、MCP 输出和已启用的诊断采集可能包含原文。首次设置页展示一次说明即可，不要每次生成重复告警或要求确认。用户权限和业务执行授权仍然有效。

### 3.3 配置与默认值

建议采用一个简单配置，而不是多种默认保留策略：

```yaml
# 新配置示意，不表示当前仓库已存在这些键。
redaction:
  mode: off  # off | on
```

安装级默认 `off`；项目可以显式设为 `off` 或 `on`，未配置项目继承安装级。界面清楚显示“生效模式”和“来源”，例如“关闭（项目设置）”。项目设置优先于安装默认；LLM 的工具参数不能擅自改变项目持久策略。

配置建议返回：

```json
{
  "redaction": {
    "mode": "off",
    "source": "project",
    "policy_version": 3
  },
  "generation": {
    "default_mode": "quick"
  }
}
```

`policy_version` 用于配置更新及缓存失效，不是新增复杂审批流程。没有项目上下文的系统日志采用明确的安装级配置；项目请求和执行任务使用已解析的项目策略，不能依赖可变全局字典。

### 3.4 统一处理位置

阶段 2 必须形成完整但有边界的调用点清单：

- REST/MCP 入参检查、Pydantic 校验器、Evidence 归一化和 FlowSpec 敏感拒绝。
- MCP/HTTP 输出、请求预览、执行记录、报告、复制、导出和前端遮盖。
- 日志 Formatter、结构化事件、异步 Worker、调试和错误处理中存在的内容识别。
- Skill 的“必须脱敏”“只允许 secret 引用”“发现敏感字段就停止”等规则。

纯语法、代码执行和引用安全函数不能因文件名带 `security` 就整体删除。尤其要区分 `contains_sensitive_flow_spec_value` 与表达式安全校验。

建议向各服务注入不可变的有效策略；`off` 在任何敏感遍历前直接返回原值语义。可以保留现有函数作为 ON 分支内部实现，避免一刀切删除后破坏显式开启场景。不要创建一套和当前配置体系平行的新全局状态。

### 3.5 原始请求与显示副本

无论 ON/OFF，真实业务请求的 ID、金额、Token 和字段绑定必须保持正确。ON 仅针对明确需要脱敏的输出/存档副本工作，不能直接修改执行中的原始对象，不能将 `***` 当成后续接口参数。

OFF 不得改变类型，尤其不要把 `null`、空串、`false`、0、数组或长编号变成其他值。原始契约将长 ID 定义为字符串时，全链路保留字符串，避免前端数字精度损失。

### 3.6 迁移与缓存

新安装默认 OFF。旧安装中没有用户显式选择、只是代码强制开启的逻辑迁移为 OFF；已有明确用户配置 ON 的项目保留其选择，禁止用真假判断把显式 `false` 当作未配置。

开启/关闭后，配置 API、预览、报告、MCP 返回和相关缓存需按策略版本失效。排队任务开始执行时确定有效策略并固定到执行上下文，运行期间不混用多个策略；界面显示该次记录使用的策略。已生成的历史制品保留原状态，不伪装恢复已经被替换掉的原文。

新增配置、数据库字段或枚举必须有对应迁移与回滚。回滚前备份；不能承诺已被脱敏的数据能还原，也不能宣称回滚能够收回已经导出的原文。

### 3.7 脱敏验收

| 编号 | 用例 | 预期 |
|---|---|---|
| RED-01 | 新安装，不设置任何脱敏配置 | 生效模式 OFF |
| RED-02 | 旧安装无显式策略升级 | OFF，不继续隐藏强制开启逻辑 |
| RED-03 | OFF 下提交业务编号、手机号样式和测试邮箱 | 不扫描、不改值、不阻断 |
| RED-04 | OFF 下提交合成的 Token、Password、Cookie、Authorization | 在原有授权输入输出中原样保留，无字段例外 |
| RED-05 | OFF 下敏感检测函数被替换成“调用即抛错”的测试桩 | 正常链路不触发测试桩，证明没有扫描 |
| RED-06 | ON 后重复同样测试 | 按显式配置执行识别与脱敏 |
| RED-07 | ON 状态生成实际业务请求 | Wire 请求仍是有效原值，显示副本可脱敏 |
| RED-08 | A 项目 ON、B 项目 OFF 并发 | 策略互不污染 |
| RED-09 | 修改策略后查询预览、报告、导出、MCP | 无错误缓存复用；历史不可逆状态明确 |
| RED-10 | OFF 用户访问无权限项目或只写 Secret 资源 | 依旧权限拒绝，不扩权 |
| RED-11 | 日志 Body 采集关闭、脱敏 OFF | 不额外采集 Body；已采集字段不自动遮盖 |
| RED-12 | 完整升级与全新 Windows 安装包 | 默认值和服务端、前端、Skill 一致 |

测试只使用合成凭据和样本，不把用户真实 Token 写入测试文件或提交记录。

## 4. 接口导出修复

### 4.1 修复范围

当前四种格式为 HAR、cURL、Bruno、Excel。先复现中文项目名触发的响应头问题，再对四条格式路径逐项检查。不能因为找到一个共享缺陷，就宣布用户所有导出问题已经解决。

参考文件：

```text
backend/app/api/v1/endpoints/api_exports.py
backend/app/services/api_exports.py
frontend/src/features/api-console/api-service.ts
frontend/src/features/api-console/use-api-console.ts
```

### 4.2 实现要求

响应头使用 ASCII fallback 文件名及 UTF-8 `filename*`，正确处理引号、空格和特殊字符，避免头注入。前端优先解析 `filename*`，其次 `filename`，最后使用按格式匹配的备用扩展名。跨域部署按实际需要暴露下载文件名响应头，不全量开放其他响应头。

下载成功才显示成功提示。`responseType: blob` 的错误响应需识别 JSON/Text 错误，展示标准错误码及 Trace ID；不能把一个 JSON 错误保存为 `.xlsx`。

验证文件内容和目标工具兼容性，不只检查 200。尤其 Bruno 输出要区分“FlowTest 自定义 JSON”与工具可导入格式，HAR 和 cURL 应保留请求关键语义。若发现历史格式缺陷，按现有导出承诺做最小修复并补兼容说明，不能靠换扩展名声称支持。

不要在本轮默认执行导出的 cURL。导出 URL 的环境相关语义应明确：若需要完整地址，传明确环境并复用地址解析器；若保留模板地址，应明确标记模板，不能悄悄取第一环境。

### 4.3 验收矩阵

覆盖中文/英文/空格/引号项目名，空项目，中文接口名，GET/POST，JSON/表单等当前支持的 Body 类型，重复 Query 键和禁用参数，0/false/null，OFF/ON 脱敏，以及大于 100 条接口。

四种文件都验证下载文件名、MIME、内容可解析和导出范围。超出当前导出上限要提示，不默默截断。接口缺版本、权限不足、包依赖缺失等异常有标准错误，不显示假成功。

## 5. 环境选择、请求目标与环境管理

### 5.1 状态与请求契约

采用“项目工作区当前环境”作为本轮唯一默认选择源，按用户与项目持久保存。接口管理、流程编排和执行入口显示同一有效选择；本轮不增加难以理解的隐式页签环境覆盖。

首次进入没有历史选择时，可以采用显式的项目默认环境；仅一个环境可直接选中。多环境且无默认时要求用户选择。已保存的显式环境被删除、失效或无权限时，清空并提示，不能回退第一项执行。

点击执行时冻结 `project_id`、`environment_id` 和必要配置版本。执行开始后用户切换环境，只影响后续运行，不影响已经启动的请求。历史报告显示实际执行环境，而不是页面当前环境。

### 5.2 地址解析唯一入口

必须核查并统一预览、单接口执行、工作流执行、Worker/Runner 和 MCP 中所有目标地址解析逻辑。不要在每个调用方拼一次 URL。

建议解析结果包含：

```text
project_id
resolved_environment_id / environment_revision
effective_service_id
endpoint_id / endpoint_revision / endpoint_variant（存在时）
base_url
request_path
resolved_url
resolution_source
```

具体字段名复用现有 DTO。界面至少展示环境名、最终 URL 和“环境地址 / 服务 Endpoint”来源。

### 5.3 推荐解析规则

| 场景 | 行为 |
|---|---|
| 普通单服务接口，无显式服务绑定 | 使用所选环境 `base_url` |
| 节点/接口/环境明确绑定服务 | 只在同项目、同环境、该服务下选择 Endpoint |
| 已指定 Endpoint variant | 严格匹配该 variant，缺失时报错 |
| 服务 Endpoint 不存在或有歧义 | 返回明确错误，不能跨环境寻找可用地址 |
| 地址以绝对 URL 存在 | 明确显示固定地址语义，按现有规范迁移/确认；不可表面选 B、实际仍固定请求 A |
| 环境不存在、已删除或不可访问 | 阻止执行，要求重新选择 |

服务选择优先级可沿用当前明确约定；若尚未形成约定，采用“节点显式服务 > 接口绑定服务 > 环境默认服务”，最终 Endpoint 仍必须受当前环境约束。普通单服务 fallback 不可吞掉显式多服务配置错误。

### 5.4 Base URL 路径前缀

必须覆盖用户实际形式：

```text
环境地址： http://10.10.203.182:38081/jscpco-api/jscpco-charge-manage/
接口路径： /bill/invoice/list
预期路径： /jscpco-api/jscpco-charge-manage/bill/invoice/list
```

这只是地址拼接测试输入，不授权向该地址发请求。避免通用 URL join 让开头 `/` 覆盖网关前缀，也避免重复添加前缀。定义“服务相对路径”的契约，针对原导入绝对地址、已经含前缀的路径给迁移或诊断，不能靠任意字符串替换猜测。

### 5.5 管理入口与生命周期

在选择器旁增加“管理环境”抽屉，复用后端 PATCH 实现编辑名称、地址、变量、请求头和已支持配置。变量及 Header 支持基本 JSON/键值校验，错误不能吞掉用户输入。

环境删除首版使用软删除或与现有资产生命周期一致的归档语义。名称为“删除”时，确认文案说明保留历史、不再用于新执行。项目默认环境、任务引用及活动执行需检查；返回结构化引用信息，不隐式删除关联任务。

删除后清理相应当前选择与缓存。列表、搜索、新执行选择器排除已删除项，历史执行仍可通过快照展示原环境信息。并发下删除与调度需要有可验证的一致性，不允许检查完引用后另一请求新增引用导致悬挂资产。

### 5.6 环境验收

使用两个本地 Mock 服务 A/B 返回不同标识，逐项验证 Preview、单接口、工作流、Worker 的目标；只看页面名称不算通过。覆盖模块切换、刷新、项目切换、删除、配置更新、缓存失效、带网关前缀、显式服务缺 Endpoint、绝对 URL 和运行中切换。

## 6. 工作流删除与接口选择

### 6.1 工作流删除

在工作流列表和当前编辑器的“更多”菜单提供删除入口。补齐服务层、权限、引用检查、前端调用和测试，不允许仅前端移除列表项。

无引用且没有活动执行的工作流可确认删除；被测试计划、定时任务、其他工作流/子流程引用时，列出引用位置并阻止直接删除。已有历史报告和执行快照保留。活动执行不被隐式终止。

删除当前工作流时关闭对应页签并清理本地草稿；延迟中的保存请求不能在删除后把资产恢复出来。重复删除采用项目现有幂等语义并固定测试，不能有时 204、有时 500。

### 6.2 接口选择弹窗

复用接口管理的查询服务和主要列表展示，新增专用选择场景，不复制整页业务状态。支持中文名称、路径、说明搜索，方法筛选，已有目录/服务筛选，分页、清空搜索、预览和选中。

推荐列：接口名称、方法、路径、目录/服务、版本、选择。首次加载不要求拉全量，搜索在服务端完成；超过前 100 条的接口仍能找到。200～300ms 防抖是初始建议值，不作为无法调整的要求。

已有节点引用不在当前页时，按 ID 读取展示信息。选中固定 `api_id + version`，不是靠名称或不可靠 `operationId` 识别。切换节点 API 前提示字段覆盖影响；不要把旧 API 的无关字段映射无提示套给新 API。

首版“选择后添加/替换一个节点”即可；多选批量加节点、最近使用可作为后续增量，不阻塞本轮。

## 7. 多页签工作区与草稿持久化

### 7.1 三类状态分离

1. 工作区状态：打开页签、激活页签、当前项目和环境。
2. 编辑草稿：节点、连线、参数、字段映射、未保存标记和基础版本。
3. 远端查询缓存：接口详情、变量、报告、环境列表等服务器事实。

页签组件只是导航层。草稿应由外部 Store/Repository 管理，页面卸载不删除草稿。复用现有 React 和状态管理依赖，不为本轮整体升级框架。[R13]

### 7.2 身份模型

建议编辑资源键：

```text
server_instance + user_id + project_id + resource_type + resource_id
```

未保存新资源采用稳定临时 UUID。`workflow_id`、API ID、变量页面应纳入各自资源身份；query 中 `focus` 对应资源键，`proposal` 属于独立提案上下文，不应被忽略而复用错误页面。

查询关键字等临时列表状态不必让每次搜索都创建新页签。跨项目切换保留草稿但清楚标记所属项目；激活其他项目页签时同步切换项目上下文，禁止旧项目草稿带着新项目 ID 保存。

### 7.3 持久化和生命周期

结构化编辑草稿优先使用 IndexedDB；小型页签元信息可使用现有持久化方案。自动保存的是本地草稿，不是自动发布版本。防抖保存之外，切换模块/关闭页签时应处理尚未落盘的最新改动；不能只靠浏览器卸载时的异步写入保证数据安全。

草稿记录包含 schema version、resource key、base revision、更新时间、内容和编辑版本号。保存失败或空间不足必须展示“本地保存失败”，保留内存编辑，不能显示已保存。采用不可变更新或明确的同步机制，避免异步旧写覆盖新草稿。

服务端保存使用已有 `expected_revision`。服务端版本变化时保留本地内容，提示冲突和比较，不覆盖远端也不静默丢弃本地。成功保存后更新基础版本，只有确认没有更新的本地编辑时才清理 dirty 状态。

退出登录清理当前会话内存和浏览器草稿；刷新/重启浏览器在同一授权会话下可以恢复。若产品需要跨登出保留，另行显式设计用户授权及隔离，本轮不扩展。

### 7.4 交互规则

支持激活、关闭、关闭其他、关闭全部非固定页签，未保存页签显示标识。关闭 dirty 页签提供“保存 / 丢弃 / 取消”；批量关闭不得静默丢草稿。

恢复后保留节点坐标、连线、参数、映射和关键画布视图。撤销历史本轮要求同会话切换保留；浏览器完全重启可只恢复当前草稿，不必持久化无限撤销栈。

变量管理新增变量后，相关查询缓存失效；回到工作流可选到新变量，同时保留原草稿。不要因一次后台详情刷新直接重置编辑器。

### 7.5 多页签回归

| 编号 | 场景 |
|---|---|
| WS-01 | 编排一半 → 变量页新增变量 → 返回：内容不丢且新变量可用 |
| WS-02 | 两个不同工作流各自修改 → 来回切换：草稿不互串 |
| WS-03 | 同名工作流分属两个项目：身份隔离 |
| WS-04 | 立即切页、刷新、浏览器后退前进：最新草稿可恢复 |
| WS-05 | 关闭一个/关闭其他/关闭全部：dirty 确认正确 |
| WS-06 | 服务端版本已变化：冲突提示、本地内容保留 |
| WS-07 | 删除打开中的工作流：页签和草稿不残留，不被延迟保存复活 |
| WS-08 | 后台 refetch、切环境：不重置业务编辑内容 |
| WS-09 | 本地存储失败、多个浏览器窗口：失败提示与版本处理明确 |
| WS-10 | 登出/换用户：不得看到前用户草稿 |

## 8. 轻量 MCP：按人工测试方式生成

### 8.1 双模式，而不是多层复杂模式

`quick` 为默认：已有接口优先，按需少量代码/数据阅读，每个指定业务先一条代表性主路径。用户明确要求异常覆盖时补少量代表用例；用户明确要求三个业务就支持三个，不能把“默认少量”变成任意业务都只能两个。

`deep` 为显式选择：保留完整证据、影响分析、覆盖矩阵等能力。轻量能力缺失时不得静默转入 deep；返回能力差异和可用升级路径。

### 8.2 调用者的最短工作路径

```text
读取/复用连接与项目能力
→ 搜索并读取相关接口
→ 只补必要参数/样本
→ 提交简明流程
→ 返回可视化提案及待补项
```

如果项目、接口和环境已经明确，跳过无必要的重复枚举。未知必填运行参数可以声明为流程输入，不因为没有当前实参而阻止创建草稿；真正执行时必须阻止缺失输入。

### 8.3 建议工具契约

优先扩展现有能力查询，返回当前项目的生成模式、脱敏生效状态、支持的 schema 和工具能力。复用 `find_assets` 等既有搜索；缺少批量详情能力时做小幅扩展，不让模型逐条读取几十个无关接口。

建议新增一个高层工具，名称示意：

```text
flowtest.propose_simple_flow
```

其职责是把已明确的业务步骤转为现有可视化提案。允许创建或修订一个提案；修订必须传 `proposal_id + expected_revision`。如果现有契约中有适合的修订工具，直接复用，不为了本文命名重复造接口。

该工具不调用外部代码/数据库 MCP，不包含内置 LLM，不执行真实接口，不自动接受/应用/发布。外部 LLM 保留理解业务的责任，平台负责确定性补齐结构、校验和持久化。

### 8.4 简明输入结构

下面仅为待实现 DTO 的结构示例，内部引用表达式应转成已有表达式模型，而不是引入第二套自由脚本语言。

```json
{
  "schema_version": "flowtest-simple-draft-v1",
  "project_id": "<实际项目 UUID>",
  "environment_id": "<实际环境 UUID>",
  "name": "流程1-开票",
  "task_ref": "<本次任务稳定标识>",
  "scenario_key": "invoice-open",
  "inputs": [
    {"name": "subsystemCode", "type": "string", "default": "p202403258"},
    {"name": "orgCode", "type": "string", "required": true}
  ],
  "steps": [
    {
      "key": "query_bills",
      "name": "查询候选账单",
      "api_ref": {"id": "<已存在接口 UUID>", "version": 1},
      "bindings": [
        {"target": "body.subsystemCode", "source": {"kind": "input", "name": "subsystemCode"}}
      ]
    }
  ]
}
```

本示例不构成完整开票 FlowSpec，也不暗示现有接口版本一定是 1。真实生成必须读取实际契约。DTO 中 steps、input、assertion、polling、binding 等采用强类型结构或受约束联合类型，禁止无限 `dict[str, Any]` 绕过验证。

输入支持必要的断言、提取、条件选择、有界轮询和输出声明；优先复用现有底层能力。用户不需要手写 Start/End、坐标、内部 provenance、编译指纹和完整中间产物。

### 8.5 服务端轻量执行路径

```text
授权及范围检查
→ 解析已有 API ID/版本与目标环境
→ 验证并归一化简明输入
→ 生成内部辅助节点与布局
→ 执行一次必要静态校验
→ 幂等持久化现有可视化 Proposal
→ 返回摘要及诊断
```

不强制 Test Context，不强制外部 Evidence，不要求模型先提交完整 Integration Plan。不伪造空证据去骗过现有 `require_proposable`；为轻量提案建立真实的 `origin_kind=quick` 等来源判别，复用提案存储和审核能力。deep 来源继续遵守自身证据约束。

如现有 UI 强依赖 compilation/context，需要让 UI 正确呈现轻量来源及可选字段，而不是制造一个假的成功 Context。

### 8.6 返回状态必须诚实

建议把不同维度分开：

```json
{
  "proposal_id": "<实际 ID>",
  "proposal_revision": 1,
  "generation_mode": "quick",
  "status": "draft_created",
  "static_validation": "passed",
  "readiness": "needs_input",
  "missing_inputs": ["orgCode"],
  "execution_status": "not_run",
  "review_url": "<实际审核路径>",
  "diagnostics": [],
  "timings_ms": {"resolve": 10, "compile": 20, "validate": 15, "persist": 10}
}
```

数字只是结构示意，不是当前性能数据。将工具错误通过 MCP 支持的结构化结果和错误语义表达，避免把整段错误埋进普通成功文本。[R14]

字段不齐但能够构建合法输入参数的提案，允许 `needs_input`；引用不存在或结构不合法时不能保存为“静态通过”。如保留失败草稿用于继续修改，其状态必须明确为 incomplete/invalid，不可进入执行。

### 8.7 幂等、修订与部分成功

每个流程使用独立、稳定的幂等键，两个流程共享 task_ref，但不宣称原子创建。A 成功而 B 失败时保留 A，只继续 B。

同键同规范化内容返回已有提案；同键不同内容返回冲突，不覆盖。修改内容后使用新的操作幂等键并附 expected_revision。网络超时后先按幂等键/任务引用查询状态，不盲目创建新流程。

修订只修改目标提案，不覆盖用户较新版本；已审查提案内容变化需正确更新审核状态。接受、应用和发布仍是后续独立动作。

### 8.8 轻量来源与身份

内部始终使用项目范围内稳定 API ID + 版本。`operationId` 仅作外部契约元信息及映射线索；重复时明确报告歧义，禁止由 LLM临时编造名字冒充已导入接口。

节点有稳定机器 key，中文 name 只作展示。语义哈希可排除纯坐标、展示名，但前提是执行链不通过 name 引用。提案完整内容摘要仍覆盖全部内容，保护审查后的完整性；不能通过“名字不计入语义哈希”绕过 Apply 的版本/内容校验。

输入变量可参与断言和字段映射，但需校验类型、作用域、定义时序及可达性。不能通过改业务查询条件来绕过表达式模型缺陷。

## 9. Skills：所有入口同步，默认停止过度分析

### 9.1 必须同步的工件

至少更新 `skills/flowtest-generate-integration-flow/SKILL.md`、`manifest.yaml`、`references/workflow.md`、匹配的 examples、agents 描述和 evals。检查 onboarding、triage、coverage 等 Skill 的交叉引用，避免其旧默认又把普通生成引向重流程。

生成技能采用基础 quick 能力和可选 deep 能力；不再把 evidence-write scope、全部编译工具和外部数据库 MCP 作为普通生成必备条件。外部依赖标记 optional；用户没有安装 Skill 时，MCP 工具描述及服务端默认也必须能走 quick。

### 9.2 默认行为预算

以下是初始产品默认值，可在实测后修正，不是已实现性能：

| 预算 | 建议值 | 执行主体 |
|---|---|---|
| 每个明确业务的默认用例 | 1 条主路径 | Skill/调用者 |
| 数据样本 | 优先 1 条，每轮候选最多 5 条 | Skill及可控采样工具 |
| 补充数据库查询 | 优先不查；必要时围绕明确缺口，初始预算 3 次 | 外部调用者，FlowTest不能假装强制外部工具 |
| 同类错误修正 | 最多 2 轮，即初次加最多两次修改 | Skill、提案操作元信息 |
| 已有契约的两流程工具调用 | 优化目标不超过 15 次，失败诊断单列 | 客户端统计 |
| 首次可审查草稿 | 优化目标 5 分钟内 | 固定客户端/模型条件下测量 |

模型超出软预算时保留已经完成的成果，列出缺口，停止扩大调查。服务端只硬性控制自己的超时、数量和请求体等边界；不能声称仅靠 Skill 文本就约束所有外部 LLM 的思考时间。

### 9.3 必要信息的读取次序

先读现有接口与示例，再读项目变量和已知测试配置；遇到明确的必填字段、状态值、ID 关系缺口，才读取相关 DTO/方法或少量数据库字段。

用户明确说“结合数据库”时可读取必要样本，不能因为默认 quick 完全忽略用户要求。反之，契约已经足够时不为了“证据完整”再查数据库。禁止默认做全表 COUNT、全库分布统计、遍历无关 Mapper/Service 或拉取大批行。

冲突影响接口身份、金额、目标或关键断言时必须指出，不能瞎选。缺少可推迟到运行时的实参则声明为输入，继续生成草稿，不无限挖掘。

### 9.4 脱敏规则同步

Skill 读取有效策略。OFF 时不得自行把 orgCode、Token、密码样本等改成 `***` 或以敏感为由终止；平台不能强制把普通明文输入替换为 secret 引用。

OFF 也不要求模型读取无关凭据或把原文重复写进最终报告。使用已有引用可以更方便，但这是选择，不是隐含强制脱敏规则。

### 9.5 不允许的工作方式

不临时编写自定义计划生成器补平台缺陷；不为了传 JSON 自动创建上千个碎片；不反复重建上下文；不无限尝试同一报错；不编造 ID、业务状态或测试结果；不把“提案已经存在”说成“业务执行成功”。

这些限制用于普通流程生成，不用于压缩 Codex 修复平台代码所需的正常测试工作。五分钟生成目标不是要求 Codex 五分钟完成整个迭代。

## 10. 传输、校验和错误诊断减负

### 10.1 不让 LLM 搬运内部产物

内部编译结果保存在服务端，返回提案 ID/制品引用、摘要及差异。后续操作使用引用，不把完整 FlowSpec 来回转交外部 LLM。资源引用必须校验项目与调用者归属，不能仅凭 ID 读取跨项目数据。

### 10.2 Windows 问题的边界

截图中的长行限制还不是已验证的协议事实。用 Windows 实际安装包测试 stdin/stdout、Python/Node 适配器、字符编码、缓冲和 JSON 序列化边界。不要默认归咎于 Windows 或 MCP 标准，也不要无证据要求升级协议版本。

典型输入应通过正常工具参数一次传递。若实际超出边界，先减少内部对象回传；只有确实需要大文件才采用现有附件/资源能力或少量有界分块。不能让模型逐块搬运上千次。

### 10.3 校验收敛

一次提交返回尽可能完整的静态错误列表，每条包含错误码、节点 key、字段路径、预期、实际类型/摘要、是否可修正和建议动作。长度有界，必要时分页取剩余诊断；不只报第一个，也不返回巨量无关栈。

纯展示修改不重收外部证据；语义修改重新做相关静态检查。缓存至少包含接口版本、schema/编译器版本、语义输入和相关目标配置身份；ON 下显示处理还需策略版本，不能错误复用其他策略输出。

未知异常走标准 envelope 和 trace，不吞掉异常，不以空列表代替失败。

## 11. 开票/红冲验收场景

### 11.1 生成目标

项目“1.22发票”只是用户场景名称，必须通过实际系统查找 ID。固定输入 `subsystemCode=p202403258`。生成两个独立可视化提案，中文业务节点，不默认执行业务。

### 11.2 流程 A：开票

```text
查询候选账单
→ 从有界候选中校验开票规则
→ 选取一条满足条件的账单
→ 查询必要收费项/补齐必填参数
→ 提交一次开票
→ 有界查询状态
→ 验证最终业务状态并输出关联标识
```

### 11.3 流程 B：红冲

```text
接收流程 A 输出标识
→ 精确查询同一开票对象
→ 检查是否满足红冲前置条件
→ 提交一次红冲
→ 有界查询状态
→ 验证红冲结果
```

handoff 中的标识必须来自实际契约：可能需要账单 ID、发票 ID、项目及环境信息，不预先假定一个 `openedBillId` 就能完成所有操作。绑定合法的已有输入/输出模型，不能通过聊天记忆拼接，也不能任意找一条历史发票红冲。

### 11.4 关键断言与副作用

读取接口实际定义后确认 HTTP 成功、业务成功、关键标识非空、同一对象关联和最终状态。未知的业务枚举不能硬写成常见值。没有候选数据时显示前置数据不足；状态仍处理中则在轮询上限到达后标为超时/未完成，不算成功。

轮询次数、间隔和总时限以业务契约为依据并允许配置。只重试状态查询，不自动重试开票、红冲等非幂等提交；提交超时时优先查询受理状态，不能盲目再次提交。

两个流程的独立运行和组合运行不同：单独运行 B 必须显式提供对应 A 的 handoff；缺失或目标环境不匹配时阻止执行。需要执行时另行取得明确授权，默认使用 Mock 回归，不发出真实开票。

## 12. 最小可观测性与性能验收

只增加任务级和阶段级必要埋点，不建设新观测平台。客户端记录总墙钟时间、工具开始/结束、失败和首个草稿时间；服务端记录解析、编译、校验、持久化和传输字节数。并发阶段时间不能简单相加当作总时长；服务端无法测得的外部 LLM 时间标为客户端侧/未知。

建议首轮基准：两个流程，每个不超过 10 个业务请求步骤，已存在契约、环境和必要样本；正常简明请求体目标小于 64 KiB。该大小是设计目标，不应在未核对实际可用能力前变成任意拒绝用户流程的硬限制。

| 指标 | 初始目标 | 说明 |
|---|---|---|
| 确定性轻量提交服务端耗时 | 本地固定基准 p95 ≤ 5 秒 | 至少 20 次重复；记录硬件、数据库、版本和冷热条件 |
| 两条首次可审查草稿 | 固定客户端/模型下 ≤ 5 分钟作为目标 | 首次项目导入/深度分析单独统计 |
| 相同错误无限循环 | 0 | 最多两轮修正后明确停止 |
| 内部 FlowSpec 反复往返 | 0 次必要性之外的搬运 | 使用服务端提案/制品引用 |
| 静态通过冒充执行通过 | 0 | 分开状态 |
| OFF 默认路径敏感识别器调用 | 0 | 用测试桩证明 |

实际不足 20 次的统计不能冒充稳定 p95，固定样例通过也不能宣称整体“95% 生成准确率”。未达目标如实报告瓶颈，不调低断言、不增加假成功。

## 14. 回归和发布门槛

### 14.1 测试层级

单元测试覆盖策略、选择器、地址解析、文件名、草稿状态和输入归一化；集成测试覆盖 API、权限、幂等、持久化、删除引用与缓存；前端测试覆盖页面交互和状态；Playwright 使用本地 Mock 验证完整用户任务。

根据仓库 AGENTS 和脚本执行必要检查。参考基线的要求包含后端格式/lint/typecheck/pytest，前端格式/lint/测试/build，以及 Compose E2E；以当前工作区规范为准。[R01]

所有测试范围必须明确区分：已执行通过、已执行失败、未执行。不能因 Docker、Windows 或依赖不具备而写“应当通过”。

### 14.2 组合关键用例

完整回归至少包含：中文项目四种导出；两个 Mock 环境正确切换；带网关前缀的最终 URL；环境失效不回退；引用中的工作流不能直接删除；第 200 条接口可被选中；两个项目各自两个工作流互不串稿；刷新恢复；OFF 合成 Token 原样经过 MCP/预览/导出；ON/OFF 并发隔离；轻量生成不要求 Evidence scope；两流程部分失败可恢复；中文节点修改不重采证据；声明输入可参与断言；超时幂等查询；关闭页签与删除不复活草稿。

### 14.3 阻断发布的问题

请求错环境、丢草稿或串项目、OFF 仍有强制脱敏/敏感拒绝、绕过访问权限、错误参数绑定、重复创建提案、生成时擅自执行业务、历史记录损坏、安装包缺新工具/迁移，以及关键回归失败，均阻断本轮发布。

次要视觉细节、多选批量加节点、最近使用、长尾性能优化可以记录后续，不得拖住核心闭环。性能目标未达到时不能宣传已达标；是否发布功能修复与性能增强可拆分评估，但上述正确性门槛不能放宽。

## 15. 打包、升级和兼容

新增 MCP 工具、配置默认值、前端静态资源和数据库迁移都必须进入 Windows 独立包。源码可用但安装包工具缺失，不算交付。

检查当前实际打包脚本、冻结依赖、模块发现和 Skill 分发方式；不要猜测目录。用干净安装包确认 tools/list、工具 schema、有效 OFF 配置、quick 默认和完整生成链。

保留 deep 既有工具，客户端通过能力发现判断 quick 是否支持。更新 manifest 与工具版本声明，但不要无必要升级全部依赖和 MCP 协议。老客户端收到清楚的能力提示，不调用不存在的新工具，也不静默回到两小时重流程。

升级前备份数据库和本地配置；迁移支持重复运行或可靠的版本管理。新草稿存储有 schema version，不让旧浏览器缓存覆盖新格式。回滚流程记录数据库、配置、静态资源和打包版本的一致性；数据不可逆部分明确提示。

## 16. 文档和仓库规则同步

参考基线 `AGENTS.md` 存在对原文日志和 Secret 的约束。[R01] 本次用户明确要求默认不脱敏，因此实施时应指出冲突，并在 S2 中显式、最小地更新与自动脱敏有关的仓库规范、文档和测试期望。不能一边保留“无条件遮盖”规范，一边宣称默认 OFF 已生效。

与脱敏无关的鉴权、加密、项目隔离、只读数据库访问、任意代码执行限制和业务执行审批不得借机删除。也不得修改锁文件、认证逻辑或工程规范来掩盖不相关测试失败。

代码标识符和类型使用英文，UI、业务节点及产品文档用中文。保持现有 UTF-8/BOM/换行规则；先读实际编码说明，仅最小 diff，禁止全仓库重编码。本项目是 GitHub 工程，不套用用户其他 Java/SVN 项目的管理规则；仍不得未经授权 push、merge 或改写历史。
