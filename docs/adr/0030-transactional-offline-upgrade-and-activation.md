# ADR 0030：事务式离线升级、自动回滚与目录激活

状态：Accepted
日期：2026-08-19

## 背景

S33 的离线升级会在切换镜像前生成一致性备份，但新版本启动失败后只提示人工运行恢复命令。
这会把故障处理留在最紧张的维护窗口，并可能出现“旧镜像 + 已迁移数据库”的错误组合。
此外，升级成功后的新解压目录没有 `.env`，日常脚本仍依赖旧目录，活动安装边界不清晰。

## 决策

1. 新包必须先完成逐文件摘要、镜像 ID 和架构校验；只有随后生成 PostgreSQL + MinIO 一致性备份，
   才能启动新镜像。备份记录旧包的 `SOURCE_REVISION`，不依赖目标机目录是否为 Git 仓库。
2. 新版本启动或 Readiness 失败时，升级器使用旧目录的 `.env`、`images.env`、Compose 和 `restore.sh`
   自动覆盖恢复数据库、对象集与旧镜像。回滚成功后命令仍返回非零，禁止把“已恢复”误判为“升级成功”。
3. 任意升级尝试都写入不含路径和凭据的 JSON 证据，状态固定为 `passed`、`rolled_back` 或
   `rollback_failed`，并记录失败阶段、回滚状态、起止时间及新旧 VERSION/SOURCE_REVISION/SOURCE_STATE。
4. 自动回滚失败时保留备份并要求立即停止写入、人工恢复；不得只切换旧镜像或继续业务验证。
5. 只有新版本通过 Readiness 后，才把旧 `.env` 以 `0600` 复制到新目录。失败升级不复制凭据；
   不同的新目录若已经存在 `.env`，升级必须拒绝覆盖或混用。
6. 工具不修改由公司运维维护的 `current` 符号链接。只有 `status=passed` 后才能由变更流程切换链接；
   旧目录和升级前备份继续保留到观察窗口结束。
7. 受控失败注入只在显式设置 `FLOWTEST_S36_FORCE_POST_START_FAILURE=1` 时生效，用于在新服务已经健康后
   验证自动回滚。该开关不改变正式升级的成功判断，也不能把短测当作真实升级审批。

## 结果

Compact 离线升级形成“校验 → 备份 → 启动 → 验收 → 激活”闭环；失败路径能恢复匹配的旧数据与镜像，
成功路径留下可独立运行的新目录。自动回滚降低维护窗口风险，但不能消除跨版本不可逆迁移评审、
业务停写、备份托管、72 小时试点和人工签署要求。
