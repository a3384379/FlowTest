# FlowTest 修改正确性复审：残余问题修复方案

日期：2026-10-22。基于[本轮审计报告](scope-followup-audit.md)确认的 4 个 P2 问题。本文件保存实施前方案及复审追加合同；实际完成状态见[整改实现记录](scope-followup-implementation.md)，不能把方案文字本身作为修复证据。

## 1. 目标与约束

补齐“写请求可能已执行，但响应因组织身份改变被丢弃”后的原范围缓存协调。正常成功、普通卸载、组织切换、失败恢复和再进入必须有明确行为；保留现有响应身份隔离、权限检查、一次性 Secret/token 保护、草稿及版本选择。

不自动重发写请求，不放宽 API 响应身份检查，不把新组织身份用于原组织数据重读，不把用户输入当作已确认的服务端结果。只处理本轮四项残余，其他模块和已有无关警告另行跟踪。

## 2. 统一行为合同

| 场景                            | 原范围缓存                                                             | 当前页面反馈                               | 写入行为                       |
| ------------------------------- | ---------------------------------------------------------------------- | ------------------------------------------ | ------------------------------ |
| 正常成功，身份未改变            | 按现有合同更新或失效，并等待必要刷新                                   | 原命令仍有效时显示成功与结果               | 一次请求                       |
| 页面卸载，身份未改变            | 原范围仍更新或失效                                                     | 不向已离开的工作区回写弹窗、表单或一次性值 | 一次请求                       |
| 响应被转为 SessionBoundaryError | 标记原范围失效，使用 refetchType: none；需要协调稳定缓存的另做消费设计 | 保留身份隔离，不在新范围显示原命令成功结果 | 不自动重试                     |
| 返回原身份和原项目              | 实际读取权威数据，完成后更新消费者                                     | 权限或对象状态按有效读取收敛               | 只读请求；用户明确操作才再写入 |
| 普通业务或网络错误              | 保留输入和现有错误语义；是否重读按原接口合同决定                       | 原命令仍有效时显示标准错误                 | 不自动重试写入                 |

发起命令时捕获不可变的 projectId、apiId 和相关团队身份。错误分支使用 `instanceof SessionBoundaryError`，不依赖错误字符串，也不把所有异常统一解释为服务端未写入。

现有四处呈现相同的稳定行为，但不必为此次修复直接引入全局 mutation 框架。只有多个落地点已验证完全一致的原范围失效策略才考虑提取小型、显式类型的公共函数；接口稳定定义的恢复与权限消费者应保留自己的合同。

## 3. C-M06-01：成员权限协调

涉及文件：`frontend/src/features/projects/AccessManagementPanel.tsx`；必要时核对 `ProjectProvider.tsx` 和各权限消费者，不预先扩大重构。

1. 在命令参数中固定原项目和受影响团队，避免回调依赖已切换页面的选择状态。
2. 边界错误分支失效原项目的 `project-permissions` 全部后缀、单数 `project-permission`、项目摘要、成员和团队授权；项目目录使用实际存在的 key。团队与目录缓存按真实受影响范围处理，不能为了方便构造不存在的带 projectId 的 key。
3. 所有边界失效使用 `refetchType: 'none'`，不在新组织身份下读取原项目。保持原成功路径的逐键刷新汇聚及等待全部完成后再解除 pending。
4. 返回后通过真实权限查询确认角色。权限读取失败时继续采用当前失败收敛，不使用旧 Owner 兜底；后端授权保持原样。
5. 当前用户仍为合法 Owner、Editor 或系统管理员时，原有操作能力不受影响。

新增正式回归优先放入现有 `ProjectsPage.test.tsx` 或权限组件测试，复用真实 SDK 与身份拦截器。必须覆盖普通非系统管理员、另一名 Owner 存在、Viewer 团队回退的合法自移除路径。

验收：切换组织后的原权限失效；其他项目权限不受影响；新组织期间无原项目 GET；返回后有效角色为 Viewer，真实消费者的编辑入口收敛；读失败时也不能使用旧 Owner；写请求始终一次。

## 4. C-M15-01：报告通知目录协调

涉及文件：`frontend/src/features/reports/use-reports.ts`；回归位于 `ReportsNotificationsIsolation.test.tsx`。

1. 创建与启停 mutation 在类型化边界错误中，根据各自输入的原 projectId 失效 `notification-webhooks`，不触发当前身份下的读取。
2. 保留当前命令身份守卫、项目工作区重建和 pending 输入锁定。原范围 Secret 不能流入新页面；不缓存、不日志记录或再次索取已丢弃的一次性 Secret。
3. 返回原项目后目录实际重读，创建项或启停结果反映真实服务状态。

验收：创建与启停各自覆盖成功、普通错误、普通卸载、组织切换、快速返回；原项目正确失效，其他项目不失效；组织切换期间无原项目 GET，无错范围 Secret 或成功提示，无自动重复 POST/PATCH。

## 5. C-M19-01：发布判断目录协调

涉及文件：`frontend/src/features/release-gate/use-release-gate.ts`；回归位于 `ReleaseGatePage.test.tsx`。

1. 创建判断 mutation 在边界错误分支同时失效原项目的 `release-decisions` 所有分页及 `release-latest-decision`。
2. 不修改判断计算、发布策略、证据快照、发布记录或当前失败返回值的语义；身份改变后不向另一工作区展示原判断详情。
3. 保留提交期间证据选择、搜索、分页和表单锁定，正常成功路径等待刷新；不以自动重试补偿身份边界异常。

验收：原目录和最新判断同时失效，当前其他项目缓存保持；返回后实际显示已创建判断；一次提交只有一次 POST；正常慢刷新、服务错误后的输入保留与显式重试仍通过。

## 6. C-GLOBAL-01：接口定义与标签恢复

涉及文件：`frontend/src/features/api-console/use-api-console.ts`，必要时 `WorkspaceObjectTabs.tsx` 与显式查询键定义；回归位于 `ApiConsolePage.test.tsx` 和 `WorkspaceObjectTabs.test.tsx`。

1. 在边界错误分支取消准确原项目、原接口的各版本详情请求；维持成功路径既有取消与 `throwIfAborted()` 防线，避免旧 GET 反写定义。
2. 失效原接口详情各版本、列表及相关稳定定义；全局搜索只处理现有受影响范围，不把当前接口选择切到原对象。
3. 为稳定定义安排可执行的恢复读取。当前稳定键仅由 `setQueryData` 写入，标签通过 `getQueryData` 优先读取，因此“失效一个没有 queryFn 的键”不能独自完成修复。
4. 最小方案先验证返回原工作区时现有详情读取是否能可靠更新所有已打开标签；若非活跃对象仍无读取入口，则为失效的打开对象增加受身份约束的定义/详情读取，或让标签基于可刷新的权威读取恢复。只在原身份有效时执行，不在新组织范围读取原项目，不引入后台轮询。
5. 保持当前 A 与被改名 B 的独立性、固定版本选择与本地草稿。未知写入结果期间不把输入字符串当成真实名称覆盖缓存。

验收必须经过真实标签消费者：A 当前激活、B 非活跃且有旧定义；发起 B 重命名，切换组织后放行成功响应，返回原身份，完成权威读取后 B 标签显示真实新名称，A、B 草稿及版本均保持。再覆盖原详情旧 GET 在取消后迟到的情况，确认不能反写旧定义。

## 8. 验证与交付顺序

1. 先在独立分支补相应正式特征测试，确认当前代码按上述业务条件失败，保留完整日志。
2. 逐项最小修改并跑具名测试；前端格式、ESLint 与类型检查覆盖改动文件和跨文件类型。权限和共享 API 缓存的改动额外回归实际消费者。
3. 保持已有 AI、组织账号、Dashboard、工作流与数据模拟的有效回归；不修无关历史警告，不修改覆盖率或测试运行阈值。
4. 合并前对最终源码执行完整 `make check`，绑定测试时的代码校验值与提交 SHA。根据实际修改的可信路径与风险计划，完成最新 Head 适用的远程门禁；具名通过不替代正式 Required Gate。
5. 浏览器验收按风险覆盖成员权限控件、通知渠道、发布判断与 A/B 标签实际恢复，使用隔离的 Playwright bundled Chromium / Chrome for Testing。若无法执行则明确记录，不把 MSW 测试称为浏览器验收。
6. 交付报告分别列出本地具名、本地完整、最新 Head 远程门禁、合并状态和实际发布验收。没有新提交或部署时如实保留未执行状态。

完成标准：四项反例对应正式行为回归转绿；上述对照和其他范围保护保持；稳定 API 定义通过真实消费者恢复；无错组织读取、重复写入或一次性值泄露；最终提交的适用检查通过并有准确证据。未实施前不更新为“100% 已修复”。

## 9. 独立 max 复审追加的时序约束

首轮最小补修后，独立复审确认以下仍需覆盖的同范围边界，必须纳入最终实现和正式回归。

1. **旧 GET 晚到覆盖失效状态**：权限、通知和发布目录原 GET 可能已取得写入前快照，但仍未回到客户端。只标为失效后，若用户快速返回原身份，旧 GET 可以通过身份比较并覆盖新状态。边界分支须先等待取消准确受影响的 QueryClient 查询，再执行 `refetchType: 'none'` 失效；返回后权威读取完成，再放行原 HTTP 回执也不能回退。服务未消费 AbortSignal 时，HTTP 传输本身可能仍完成，验收重点是其不再写入缓存，不能宣称已经中止网络。
2. **接口恢复标记提前 GC**：对象标签名保存在本地，而无观察者的恢复标记默认五分钟回收。仅专用待恢复标记前缀保留到权威读取、正常成功重命名或会话清空，不扩大普通业务数据缓存寿命。正式回归覆盖离开六分钟后返回，真实非活跃标签仍能恢复。

成员变更涉及的 `projects` 是既有共享目录，其在途读取也需要取消后标记失效。保留其已有数据，不清空其他项目独立的权限、成员或详情缓存，不携带新组织身份主动重读；返回原项目时确认查询从 idle 正常恢复。

3. **常驻项目上下文恢复**：App 的 ProjectProvider 可能跨组织页保持挂载；返回项目时须恢复显式失效的项目目录，而不能依赖重新挂载。角色读取仅信任成功且未显式失效的结果；保持原目录优先级，不用响应到达时间决定角色权威性。
4. **显式失效权限的 pending 消费者**：缓存仍为 success 且保存旧 Owner 时，QueryCache 的显式失效状态必须同步收紧共享能力、工作流、用例、项目治理和通知入口；自然 stale 与正常后台读取不能因此降权。权限读取失败后继续只读，显式重试成功后再收敛。
5. **成员命令重开与表单锁定**：原成员写入或权限汇聚仍 pending 时，保留已显示的成员/团队表单并禁用全部输入、角色和提交。面板卸载重开后也须读取同项目的全局 mutation pending；运行入口检查最新受信权限、组件存活和同步防重，不将保留表单解释为恢复 Owner 能力。不同项目的命令不被同一 pending 锁住。
